# P9 限时活动 MQ 削峰压测报告

## 1. 结论

2026-09-22 在本机单实例环境完成“3000名不同用户同时抢500个活动名额”实压，最终结果：

| 指标 | 结果 |
|---|---:|
| HTTP请求数 | 3000 |
| HTTP受理成功 | 3000 |
| 最终SUCCESS | 500 |
| 最终FAILED_SOLD_OUT | 2500 |
| 重复/余额不足/未知错误 | 0 / 0 / 0 |
| MySQL `sold_count` | 500 |
| Redis剩余库存 | 0 |
| Redis参与用户数 | 500 |
| 活动生成Errand | 500 |
| 活动托管单 | 500 |
| 活动资金流水 | 1000（每单一借一贷） |
| SQL不变式违规 | 全部0 |

这说明RocketMQ成功把瞬时请求与资金、任务多表事务解耦；Redis Lua严格裁决500个名额，MySQL CAS、唯一索引、CHECK约束和复式记账完成最终兜底。

## 2. 环境与参数

- macOS本机，应用、Worker、发压端和Docker中间件共享同一台机器；
- MySQL 8.0.40、Redis 7.4、RocketMQ 5.3.1；
- CampusDash App单实例，Tomcat最大200线程、Hikari最大20连接；
- Worker单实例，活动消费者8线程、Hikari最大10连接；
- 请求数3000，并发度3000，活动quota=500，每个用户只请求一次；
- JDK 26用于运行，代码以`--release 21`编译。

## 3. 延迟结果

| 指标 | P50 | P95 | P99 | Max |
|---|---:|---:|---:|---:|
| API受理 | 965ms | 1695ms | 1775ms | 1936ms |
| 提交至最终结果 | 9861ms | 12172ms | 12322ms | 12545ms |

整轮墙钟时间为12614ms。API延迟包含本机3000并发连接排队；最终延迟包含RocketMQ排队、8线程消费、Redis裁决、MySQL资金事务和客户端250ms轮询间隔。

## 4. 正确性证据

`bench/scripts/verify_rush.sql`校验以下不变式均为0违规：

- 活动销量不超过quota；
- MySQL销量等于SUCCESS请求数；
- 同活动每用户最多一条请求；
- 同requestId最多生成一张Errand；
- 每条SUCCESS恰好一张托管单；
- 每条SUCCESS恰好两条等额借贷流水；
- SUCCESS不存在无Errand记录；
- 跑腿员容量快照与实际占用一致。

## 5. 实压发现并修复的问题

第一次实压中，64字符以内的`requestId`拼接`rush:escrow:`后超过`wallet_ledger.biz_no VARCHAR(64)`，500次业务事务全部安全回滚。修复为SHA-256的Base64URL确定性摘要后，业务号固定55字符，重复消息仍映射到同一唯一键。

同时发现结果轮询原先先查MySQL再查Redis，3000用户轮询会反向打满数据库连接池。现已调整为Redis优先、缓存缺失才回源MySQL，恢复任务负责补回成功结果缓存。

第一次失败留下的500条RocketMQ重试消息在Worker重启后成功完成，证明消息未丢失；为避免这些历史重试污染客户端统计，最终报告使用全新活动ID 90002执行。

## 6. 复现方式

```bash
bash bench/scripts/seed_rush.sh

# 分别启动App（需为压测显式开启测试身份头）和Worker后执行：
java -cp dash-bench/target/classes com.campusdash.bench.RushLoadClient \
  --mode async --requests 3000 --quota 500 --concurrency 3000 --campaign 90001

docker exec -i -e MYSQL_PWD=dash123456 dash-mysql \
  mysql -uroot -D campus_dash < bench/scripts/verify_rush.sql
```

这是同机功能和容量基线，不等价于生产容量结论。正式容量评估还应拆分发压端与服务端，并采集Broker积压峰值、MySQL活跃连接峰值和容器CPU/内存曲线。
